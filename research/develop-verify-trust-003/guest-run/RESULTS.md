# TRUST-003 guest run (ENDO-11): the IA1–IA4 matrix against a separate verifier principal

**Verdict: BOUNDARY DEMONSTRATED, in a disposable guest only.** Two installed runs completed in an Arch Linux guest. A restricted agent (uid 1500) attacked the TRUST-002 verifier, which ran as its own locked principal (uid 968). Every T6/T7/T8/E6 control and every supplementary probe (291 applicable system calls) was refused by the kernel. All 32 rows held. Sixteen authentic PASS records went to correct candidates, and no incorrect candidate received an authentic PASS. Interruption and restart produced INCOMPLETE, never PASS.

**What this cannot establish.** The guest has no libvirt socket, no Docker socket and no polkit rule beyond the distribution's defaults. This run therefore says **nothing** about the workstation's H0, the libvirt socket restriction (APPROVAL.md Part 2) or any polkit behaviour. It shows the separate-principal mechanism works when the principals really are distinct. It does not show that George's workstation is protected. The workstation verdict in the README is still **BLOCKED**.

## The run, in order

1. **Attempt 1 (discarded): installation defect.** Staging and `install.sh` succeeded from the original pins. However, `user@968.service` failed with `224/PAM`, and pam_unix logged *account endo-verify-002 has expired*. systemd 262's sysusers `u!` writes expiry day 1 (`!*:20776:::::1:`). As a result `verify.sock` never existed, and no request could have produced a record. The installed gate run as endoagent still reported `h0:true, closure:true` (see D2 below). The fix and its test are recorded as PROTOCOL.md **A5**. The pins were re-derived (one line changed in each list) and pushed. Both list digests were then checked again against GitHub's view of the commit before staging. Evidence: [attempt-1/](attempt-1/).
2. **Attempt 2 (stopped): a measurement artefact, and the gate refused it correctly.** Run under `strace`, `sudo -n true` printed *sudo: effective uid is not 0, is /usr/bin/sudo on a file system with the 'nosuid' option set…* and exited 1. The gate's `sudoRefused` rejected that, which is right: it is not a policy refusal. Both runs stopped at IP0 with exit 3 and recorded no rows. After that, strace was attached by root only after IP0 had passed. Evidence: [attempt-2-strace-blocks-sudo/](attempt-2-strace-blocks-sudo/).
3. **Run proper.** Staged from commit `c3718f1d`, the content pins at `05cb46a7…` and `84aa73ec…`, and package `7b6dec22…`. Its normalized manifest is still `d1a018c4…`. Evidence: [run/](run/). The probe, matrix script and reader were updated in place from later commits. Their digests in the guest are `333965…` (probe.py), `707ac7…` (matrix.sh) and `ba6e7a…` (read-records.ts).

## Defects found

- **D1 (fixed, test, A5):** the verifier principal was declared `u!`, so its user manager could never start. This is described under Attempt 1.
- **D2 (open, no security effect):** the installed gate does not check that the verifier is running. It passed `h0` and `closure` with `user@968` failed and the socket absent. Requests then fail closed (service-unavailable), so no authority is created. The proposed fix is an `installed-socket-present` check that requires a live socket owned by the verifier. Not implemented here.
- **Tooling defects (fixed in this branch):** the probe passed 32-bit variadic arguments, which made `process_vm_readv` return EINVAL in the idle probe; both live probes passed full-width arguments and got EPERM. The reader's independent grader ran `git archive` without `GIT_NO_REPLACE_OBJECTS`, so the T5a repository's replace ref made B's commit grade as A, and the reader's `falsePasses` field is weaker than intended for that reason. The export binding used the client's environment, which disables replacement, so the bound reads are sound. The false-pass conclusion rests on the verifier's own records cross-checked against the fixtures, as described above. Grader fixed: `GIT_NO_REPLACE_OBJECTS=1`.

## What a guest pass leaves unproven

- The workstation's H0. It keeps Docker and libvirt membership, `libvirt-sock` is `0666`, polkit's `50-libvirt.rules` is in force and `/etc/polkit-1/rules.d` could not be read. None of these exist in the guest.
- The libvirt socket restriction (Part 2): whether it works and whether virt-manager and `virsh` keep working.
- A real interactive console login, as opposed to a background-class PAM session.
- Attacks the 002 matrix does not attempt: kernel or service vulnerabilities, setuid programs (`ksu` and others exist), request-triggered code execution in the verifier's parser, or a compromised root.
- The image signature (unverified; see above).
