# DEVELOP-ISOLATE-001: live Pi execution boundary

**Status: partial, offline diagnostic only.** This does not enable Everyday, change Strict, or turn Protected’s refusal into a launch. A separate process passing preflight does not establish protection for the Pi process the workbench actually talks to.

## Architecture and threat model

The trusted controller, its terminal and the canonical evidence store stay outside the sandbox. The intended boundary is unprivileged Bubblewrap (empty read-only root, explicit mounts, new mount, user, PID, net, IPC and UTS namespaces, fresh terminal session, no capabilities or further user namespaces). A transient systemd user scope registers the wrapper before it starts and confirms cleanup, including detached processes. A scope neither restricts filesystem access nor makes an unsandboxed agent safe. The first slice uses the existing experiment runner for a bounded, disposable offline session, not the live workbench launcher.

Treat prompts, the paired page, Pi tool code, descendants, plugins, MCP settings, and workspace content (including Git metadata) as hostile. The test profile admits only explicitly selected root-owned runtime files and a private disposable workspace. It does not bind the operator’s home, evidence stores, checkout, host `/run`, package caches or `/sys`. Inside it may write the workspace and private tmpfs; Git fixture metadata is read-only. Credentials and settings are synthetic; a private Pi agent directory replaces the real one. Pipes are the only controller channel; no terminal is passed through. There is no model endpoint, bridge, listener or host network route. A separate net namespace matters for host abstract Unix sockets as well as loopback.

Enforcement assumes a trusted kernel, Bubblewrap, systemd user manager, controller, and root-owned runtime and dependencies. It assumes the local operator and other host processes with the operator’s authority do not race setup or tamper with the test. It excludes kernel vulnerabilities, resource exhaustion beyond the configured limits, side channels, host-admin inspection, malicious bytes later opened or executed by the operator, and compromise of the controller or its parsers. It does not protect processes started outside this boundary. It must not be used on a checkout whose Git admin directory, sockets, nested mounts or hardlinked inodes can alias host resources.

## Gates before workbench integration

1. **Mount selection and Git.** A canonical workspace path is not an inode boundary. A bind of arbitrary working trees can include nested mounts, hardlinks, pathname sockets and Git administration links. Start with a fresh disposable workspace, or establish a race-safe admission and pinning policy. Read-only `.git` here is a fixture control, not a guarantee for linked worktrees, nested repositories or arbitrary checkout content. The workbench’s `GitProjectInspectorV0` runs Git and reads untracked files as the operator. Its existing Git flags and config overrides are useful hardening, not an OS boundary for hostile mutable content; run inspection inside confinement (including file reads), or omit it in a future contained workbench. Do not hand this diagnostic’s workspace to the host inspector.
2. **Actual process and subject.** Reuse `ProcessScopeV0.wrap` for a live keeper, but separately join the ready handshake to the exact Pi process (PID and birth identity, not a PID alone), its verified namespaces/mounts, workspace identity, private descriptors and RPC transport. Prevent in-boundary code from minting its own attestation. The attached session ID and canonical workspace root must match at each grant decision. Missing, stale, contradictory or replaced identity must fail closed; tests of the existing broker policy are not evidence that a production observer is attached. No live provider or authority changes are part of the diagnostic.
3. **Runtime and extension policy.** Arch’s `/usr/bin/pi` resolves to a Node bundle under `/usr/lib/node_modules/@earendil-works/pi-coding-agent`. The bundle also uses packaged assets/dependencies; a single CLI file is not a complete Pi runtime. Admit only a trusted installed release; validate the whole runtime/config closure and do not load workspace or operator extensions, skills, prompts, themes or MCP configuration in the first pilot. A writable fixture home must never become a host runtime/config source.
4. **Model access.** The existing experiment relay is designed for one declared OpenAI-compatible local route, over a private Unix socket with host-side admission. It needs an approved listener and upstream, and does not provide a credential-safe generic route to external providers. No provider access, credential access or model spend is part of this change. The first real Pi probe, if approved, is RPC startup and state only; it is not an Everyday pilot.
