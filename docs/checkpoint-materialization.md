# Verified isolated initial-scratch materialization (source-tree PR B)

`materializeVerifiedInitialCheckpointV0(sourceStore, replayStore, digestKey, outputParent)` in `cli/checkpoint-materialization.ts` consumes an existing `endo.checkpoint-candidate.v0` receipt. It returns either a bounded refusal or `{ status: "materialized", kind: "verified-initial-scratch-materialization", directory, session, archive, verification: "canonical-archive-bytes-equal" }`. This is a programmatic API; there is no CLI command, HTTP route or new durable receipt.

The operation calls `readVerifiedCheckpointCandidateV0` before reading restorable bytes. That reader rechecks the current source and replay stores, archive reference, keyed blob and authoritative cassette comparison. The materializer then reads the candidate's archive through the read-only keyed blob store, checks its length and canonical v1 schema, and accepts only the Pi cassette pre-execution scratch boundary. It applies the existing workspace restore in a newly allocated private directory under the operator-selected parent. An independent rearchive must reproduce the source archive **byte for byte**, including supported file bytes, relative paths, directories, executable flags, internal link targets, entry times and root time. Before success it revalidates the candidate and rereads the keyed blob. No caller can supply a replacement archive digest or boundary label.

The output parent must already exist as an absolute, canonical, operator-owned private directory, with no symlinked components. Ancestors must be owned by the operator or root and not writable by others; a root-owned sticky directory such as `/tmp` may be an ancestor, but cannot itself be the selected parent. The parent cannot sit inside either evidence store or the recorded scratch root, including a physical root reached through a recorded symlink alias. The operation uses `mkdtemp` to allocate its child and never overwrites an existing path. It checks parent and child device/inode identity before and after restoration. On failure it removes only the child it created while those identities still match; if they do not, it refuses cleanup and reports the retained path for operator inspection. A failed or incomplete tree is never returned as a materialization success. Resource bounds are 64 MiB of file content (the archive writer's limit), 10,000 entries and 128 MiB of encoded archive bytes. Unsupported archive versions, unsafe paths, outward links and special filesystem entries are refused.

This path uses synchronous Node filesystem operations and has no descriptor-relative `openat` restoration. It conservatively refuses Windows and unsafe parents. The ownership and permission checks stop other local users from replacing a selected parent in normal POSIX permissions; they cannot provide a race-free guarantee against a malicious process with the same user identity, a hostile filesystem or privileged concurrent mutation. The result is a verification of the tree at the time of rearchive and final evidence check, not an enduring seal on the destination. Callers must protect and recheck it before any later use.

The restored `models.json` may still point to the recorded proxy, and prompts or tool arguments may contain the original absolute scratch path. This new directory is **not** an immediately executable replay environment. The API never launches Pi, serves a cassette, invokes a model or tool, or contacts a network endpoint. It does not restore model state, Pi process memory, in-flight tools, outside-workspace effects, full POSIX permissions or ownership. [Cassette replay](replay.md) separately tests fresh Pi execution at the original path against captured responses; materialization tests filesystem reconstruction at a different path. A controlled continuation will need an explicit switch point, validated runtime/configuration and request identity, isolated external effects, path handling, authority, and parent/child trajectory lineage before any execution claim is possible.

This API is present only in the source tree. Published npm `0.1.0-alpha.1` and `0.1.0-alpha.2` do not include it.
