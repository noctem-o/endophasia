# DEVELOP-ISOLATE-001: verified Bubblewrap diagnostic and local-model pilot (partial)

**Status: partial, disposable diagnostic plus one local-model prompt.** This does not enable Everyday, change Strict, or turn Protected’s refusal into a launch. A separate process passing preflight does not establish protection for the Pi process the workbench actually talks to.

## Architecture and threat model

The trusted controller, its terminal and the canonical evidence store stay outside the sandbox. The intended boundary is unprivileged Bubblewrap (empty read-only root, explicit mounts, new mount, user, PID, net, IPC and UTS namespaces, fresh terminal session, no capabilities or further user namespaces). A transient systemd user scope registers the wrapper before it starts and confirms cleanup, including detached processes. A scope neither restricts filesystem access nor makes an unsandboxed agent safe. The first slice uses the existing experiment runner for a bounded, disposable offline session, not the live workbench launcher.

Treat prompts, the paired page, Pi tool code, descendants, plugins, MCP settings, and workspace content (including Git metadata) as hostile. The test profile admits only explicitly selected root-owned runtime files and a private disposable workspace. It does not bind the operator’s home, evidence stores, checkout, host `/run`, package caches or `/sys`. Inside it may write the workspace and private tmpfs; Git fixture metadata is read-only. Settings are synthetic; a private Pi agent directory replaces the real one. Pipes are the only controller channel. The shared runner starts a new terminal session via its detached spawn; Bubblewrap’s `--new-session` is defense in depth, not required for the observed result. The runner closes inherited descriptors before `systemd-run`, preserving just stdio and the three Bubblewrap control channels. In the diagnostic and protected-experiment preflight a trusted read-only observer inventories the descriptors before Node startup. The default profile has no model route. The opt-in pilot adds only the existing relay socket and read-only bridge. A separate net namespace matters for host abstract Unix sockets as well as loopback.

Enforcement assumes a trusted kernel, Bubblewrap, systemd user manager, controller, and root-owned runtime and dependencies (including the host’s Python sanitizer and the probe-only Bash observer). It assumes the local operator and other host processes with the operator’s authority do not race setup or tamper with the test. It excludes kernel vulnerabilities, resource exhaustion beyond the configured limits, side channels, host-admin inspection, malicious bytes later opened or executed by the operator, and compromise of the controller or its parsers. Bind-source paths can appear in mount metadata. Kernel keyrings and extra syscall filtering are not isolated by this profile; allow no real credentials until these are addressed. It does not protect processes started outside this boundary. It must not be used on a checkout whose Git admin directory, sockets, nested mounts or hardlinked inodes can alias host resources.

## Gates before workbench integration

1. **Mount selection and Git.** A canonical workspace path is not an inode boundary. A bind of arbitrary working trees can include nested mounts, hardlinks, pathname sockets and Git administration links. Start with a fresh disposable workspace, or establish a race-safe admission and pinning policy. Read-only `.git` here is a fixture control, not a guarantee for linked worktrees, nested repositories or arbitrary checkout content. The workbench’s `GitProjectInspectorV0` runs Git and reads untracked files as the operator. Its existing Git flags and config overrides are useful hardening, not an OS boundary for hostile mutable content; run inspection inside confinement (including file reads), or omit it in a future contained workbench. Do not hand this diagnostic’s workspace to the host inspector.
2. **Actual process and subject.** Reuse `ProcessScopeV0.wrap` for a live keeper, but separately join the ready handshake to the exact Pi process (PID and birth identity, not a PID alone), its verified namespaces/mounts, workspace identity, private descriptors and RPC transport. Prevent in-boundary code from minting its own attestation. The attached session ID and canonical workspace root must match at each grant decision. Missing, stale, contradictory or replaced identity must fail closed; tests of the existing broker policy are not evidence that a production observer is attached. No live provider or authority changes are part of the diagnostic.
3. **Runtime and extension policy.** Arch’s `/usr/bin/pi` resolves to a Node bundle under `/usr/lib/node_modules/@earendil-works/pi-coding-agent`. The bundle also uses packaged assets/dependencies; a single CLI file is not a complete Pi runtime. Admit only a trusted installed release; validate the whole runtime/config closure and do not load workspace or operator extensions, skills, prompts, themes or MCP configuration in the first pilot. A writable fixture home must never become a host runtime/config source.
4. **Model access.** The existing experiment relay was measured for one declared local OpenAI-compatible model and one prompt. It needs approved listeners and an upstream; there is no credential-safe generic route to external providers. Before using any credentials, the host proxy must be reachable **only** through the relay, and each recorded exchange must have verified host-side lineage to the actual Pi process. Reusable session-lifetime admission, external providers and credentials remain outside the tested profile.
5. **Descriptors in the actual live launch.** Reuse the shared runner’s fd hygiene or an equally strict pre-exec allowlist; observe the exact fd inventory for the executing Pi path. A file, device, pipe or connected socket descriptor can bypass path and namespace boundaries. Do not infer the descriptor table of a live launch from a different process’s preflight.

The probe also edits a copy of the capability and `NoNewPrivs` strings to test its parser, not the boundary. Hosted CI reports **absent** real sandbox coverage in the job summary if it skips the protected isolation tests; use `ENDO_REQUIRE_ISOLATION=1` on a host where that coverage is required.

### Measured local-model pilot, 2026-11-18

George supplied a loopback-only llama.cpp endpoint at `http://127.0.0.1:8090` and permitted the pilot’s temporary listeners. The host verified HTTP 200 for `/v1/models` and that `Ornith-1.5-9B-Q8_0` was listed. That host GET bypassed the recorder; the one model exchange was the one **through the relay**, not the server’s only request. Pi 1.5.2 answered `READY` to “Reply with the single word READY.” It used `-p --provider relay --model Ornith-1.5-9B-Q8_0 --thinking off`, offline/no-session and no-tools or optional resources. The private tmpfs held synthetic `models.json` (API `openai-completions`, base URL `http://127.0.0.1:18080/v1`, dummy key). `PI_CODING_AGENT_DIR` was `/home/agent`; `PI_OFFLINE=1`, `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`. No credential was staged, no live config was read, and spend was **$0**.

The existing [model relay](../../adapters/sandbox/model-relay.ts) puts the bridge on sandbox loopback and binds only the pathname socket and read-only bridge into the namespace. The host-side proxy applies the existing judge before opening an upstream connection. The policy allowed only `POST /v1/chat/completions` for the one model, one exchange, at most 128 requested completion tokens, a 32 KiB body and 1 MiB aggregate transfer.

Every private scope observed a distinct netns, no non-loopback interface and the exact pre-Node fd inventory `0,1,2`. The canary accepted zero private connections. A separate, trusted shared-network control with no Pi or relay mount connected once to that same canary, proving the listener was up. The active route also retained the reviewed workspace inode, read-only root and Git metadata, hidden synthetic host file and PID, no terminal, zero capabilities and `NoNewPrivs=1`. The pilot's abstract check was against an unused name, not a known host listener; the independent reviewer exercised a listening abstract canary in the fake-model reproduction. Removing **only the bridge** would leave the same governed Unix socket usable by a process that speaks HTTP over it; the bridge is not the boundary. Removing the listener and socket mount disables that route.

Wrong method, wrong path, wrong model and oversized body each reset a connection through the working bridge. The host judge recorded `route=2, model=1, size=1`, zero admissions before the real prompt, and four `not-forwarded` events with `forwarded=false`. The cassette labels those responses `upstream-error` for compatibility; the transport fields distinguish a policy refusal from an upstream failure. The only completed relay exchange was the real prompt. In the final run, the three sandbox-local bridges bound `127.0.0.1:18080` in separate short-lived namespaces; the four guest self-listeners bound loopback ports `42537`, `34181`, `43941` and `33431`. The host recorder and canary bound loopback ports `33669` and `42053` respectively. The Unix listener was mode 0600 in its own mode-0700 disposable directory (mounted as `/run/endo/model.sock`). All scopes ended, the two host TCP listeners refused post-close connections, and the Unix socket was gone. The operator’s pre-existing TCP `8090` listener was left alone.

**Host trust limit.** The TCP recording proxy binds host loopback, not just the private relay. Any process in the host network namespace, even under another UID, can connect to it and could consume the single exchange slot or manufacture a recorded exchange. The run against port 8090 relies on what the in-boundary probe observed and what the recorder counted; it does not include a host-side trace tying the request to Pi. An independent fake-upstream reproduction traced Pi's kernel process, scope, namespaces and connections, but could not pair the Unix peer by inode across network namespaces using host `ss`. Node's public `net.Socket` API does not expose Linux `SO_PEERCRED`; it was not collected. Even that result would identify the bridge as the immediate Unix peer, not Pi as the bridge's HTTP client. Before staging any credentials, prevent direct host access to the proxy and verify host-side lineage from each admitted exchange to the exact Pi process (PID, start time, scope and namespaces). This pilot changes neither.

Reproduce the listener-free control with the first command. The second requires explicit permission for disposable private listeners and that exact operator-provided model endpoint; it will not use an external provider or accept a different destination.
