# DEVELOP-ISOLATE-002: workspace admission and launch attestation

This follow-up is based on #152. It is not wired into the workbench, does not enable Everyday or Protected, and does not add a credential route.

## Workspace admission and Git

A list of Git overrides cannot make the existing host inspector safe against a concurrently modified repository. For example, it enumerates the names of filters before invoking Git; the repository can change between those reads. A network boundary around Pi alone does not cover the inspector's own reads. This slice instead produces a bounded private copy and runs two fixed, read-only Git operations inside Bubblewrap. It never supplies Git with the original configuration.

The caller must supply its evidence root and internal roots. Admission requires a canonical absolute workspace path and refuses overlap in either direction with those roots (by path and existing inode), symlink path components, a root mount point, nested mounts, symlinks and hardlinked files in copied entries, special files, nested Git directories, and any top-level `.git` other than a real directory. A mount whose kernel root is a filesystem subtree is also refused; this excludes common bind aliases and some legitimate subvolume layouts. Gitfiles and linked worktrees are not supported. Linux O_PATH descriptors pin each opened object before classification or reading; the copier checks mount identity, bounded byte counts and modification metadata, and stages a private copy under root-owned sticky `/tmp`. This is not an atomic filesystem snapshot or authorization to mount an arbitrary live checkout read-write.

Only a small standalone SHA-1 Git projection is copied: HEAD, index, refs, packed refs, loose objects and ordinary packs. Hooks, worktree config, includes, alternates and submodule Git metadata are not copied. A conservative check of the local config refuses unsupported fields, then substitutes a fixed generated config; none of the source values reach Git. The only operations are status and unstaged diff. No host system/global config, shell, helper path, protocol or network is available. There is no fallback to host Git or the existing inspector.

The copy preserves only the owner execute bit of working files. Fixed `core.filemode = true` lets Git report a mode-only change by reading the snapshot's metadata; neither command executes workspace files.

**Concurrent edits:** The checks compare each entry around its own copy, not all entries against one common instant. In an independent Arch review with a writer updating two files every 1 ms, 4 of 60 admissions contained values from different writer iterations and none was refused. A second metadata walk could catch some intervening edits, but would be another race rather than an atomic snapshot.

| Configuration surface | Why it cannot run here |
| --- | --- |
| `core.hooksPath`, `core.fsmonitor`, `core.pager`, `core.sshCommand` | Refused before launch; hooks omitted, pager and fsmonitor disabled. |
| `diff.*.textconv`, `diff.external`, `filter.*.clean\|smudge\|process` | Refused before launch; external diff and textconv disabled; no drivers reach Git, even if attributes select one. |
| `uploadpack.packObjectsHook`, `protocol.*.allow` (including `ext`) | Refused before launch. No upload/fetch command, helpers or protocols are enabled. |
| `include.path`, `includeIf` | Refused as data by admission; Git never parses the source file. |
| `gpg.program`, `credential.helper` | Refused before launch; no signing, authentication or provider route. |

The new tests make writable hostile Git fixtures that name a disposable canary script. They assert the exact rejected directive and the absence of the canary, plus the specific path, alias or metadata refusal for unsafe paths. A separate test changes the original after admission and checks that the generated config and copied work file are unchanged. On Arch, the opt-in test also observed a real staged/modified file in the sandbox's status and real unstaged diff, with confirmed scope cleanup. The restriction to a small standalone repository, text status/diff output, and the assumption of a trusted host operator remain; the full workbench inspector is not changed.

## Host-anchored offline Pi launch

The existing runner gets an explicitly opt-in experimental mode. Bubblewrap uses `--as-pid-1` in that mode so the trusted shim, and stock Pi after `execv`, are the same process that Bubblewrap reports to the host. The controller owns stdin/stdout and a separate inherited socketpair at fd 6. It preserves only that extra descriptor through the launcher sanitizer. There is no listener and no host network, credentials, provider, prompt or model call on this path.

1. The host records the launched child's transport endpoints. After systemd reports the exact active scope, the shim marks fd 6 close-on-exec and starts waiting there. The host checks the launcher and shim birth times, their direct parent relationship and exact cgroup, the boot ID, all seven namespaces, the mounted snapshot and cwd inodes, the original workspace's identity, the fixed shim argv and the root-managed Python executable. It also observes matching non-root UID, no new privileges, zero capability masks and no cgroup filesystem inside the guest.
2. Only then does the host generate a fresh nonce and send it on fd 6. It checks the reply and rechecks the shim before releasing it. The shim has no RPC role; it execs the pinned Node/Pi command in place. The host checks the fixed Pi executable and entrypoint inodes, the same process and transport, and retirement of the challenge fd before sending any RPC input. Neither the nonce nor its reply appears in argv, the environment or logs.
3. The only request is a correlated `get_state` on the owned stdio, before any prompt. A successful reply with an ephemeral Pi session ID is bound to the host-observed process and selected workspace, then checked again. Pi can rewrite its process title, so rechecks use executable identity and kernel image fields, not the displayed arguments. Rechecks require the same session and workspace, perform bounded local procfs and inode reads with no manager or RPC roundtrip, and latch `protection-lost` if evidence disappears, is unreadable or stops matching.

**Measured on Arch:** Bubblewrap 0.13.1, Python 3.14 and Node 26.13.1 ran stock Pi 1.5.2 in place. The host observed fd 6 with close-on-exec in the shim; the launched Pi did not retain that socket. Three runs checked a clean exit, replacing the source workspace with another inode, and making the source path inaccessible while Pi stayed alive. All reported loss and confirmed scope cleanup. A separate synthetic PID-1 launch observed a detached child in the same PID namespace and exact cgroup and verified that it went away when the scope ended. Wrong session and workspace requests were refused. The unit test injects a failed evidence comparison and an unreadable observation; no live PID reuse or privileged bind-mount substitution was attempted.

**Still a research gate:** The proof assumes a trusted host/kernel, root-managed runtime and pinned Pi package, and no hostile process with the host operator's authority. Procfs checks are point-in-time, not a cryptographic proof of every instruction or an atomic guarantee between observations. A stock RPC response is correlated to the host-owned connection, not authenticated to an individual writer: a contained descendant with inherited stdio could write a frame. Linux `SCM_CREDENTIALS` with `SO_PASSCRED` is a possible future per-writer transport, not implemented here. This does not grant `workspace` or `restricted` protection, authorize a model or credential path, or change the production provider. A future integration would map a verified workbench session/root to the lease and translate a failed observation into the existing `protection-lost` revocation path. That integration and the combined attested model route are separate decisions.

The watch checks Pi's own namespaces, not its descendants'. A descendant could enter different namespaces without changing the watched PID. Before enabling tools, independently establish and enforce the namespace policy for descendants; the offline `--no-tools` launch and detached-child cleanup test do not prove that policy.

For the opt-in Arch check, use a synthetic HOME and keep only PATH, HOME, XDG_RUNTIME_DIR and the opt-in flags. Set `ENDO_ISOLATE_HOST=1 ENDO_ATTESTED_PI_HOST=1` and run Vitest on `tests/develop-isolate-002-workspace.test.ts` and `tests/develop-isolate-002-attested-pi.test.ts`. Without the flags, only the fixture and simulated checks run; a skipped host test is not host evidence.
