# Real governed same-session continuation: PASS

On 28 October 2026, one separately approved, tool-free two-turn attempt completed with Pi 1.0.4 and a local Nanbeige4.3-33B model. The existing continuation runner reported `completed` and `verified`; a separate fresh-process call to `verifyInitialContinuationEvidenceV0` independently returned `verified`. The experiment sent **two real completion requests**. The private evidence, prompts, answers, reasoning, key and local paths are not published, so the repository alone cannot reproduce the verification.

## Protocol and identity

Execution used a clean working tree at main merge commit `2e9bc0f4119e05e902f653c867ed6699134f959b`, before this report was written. The pinned Pi executable reported 1.0.4 and matched identity digest `09fc04526699f789980ac52dbd64336c12a89f2de2ad90417bf9fcabd14cda23`. The selected child was the baseline of the retained qualified initial checkpoint and verified-pristine sibling pair. Before and after the attempt, trusted readers verified the checkpoint and both siblings with the private comparison-domain key. No prepared sibling was used as the running directory.

The operator approved starting a disposable loopback-only llama.cpp server and personally entered the exact first-plan and separate boundary approval phrases. One earlier invocation was declined before execution because the entered text did not match the first approval phrase; it sent zero completion requests. The operator explicitly requested a new plan, and the successful invocation was the only dispatched attempt. There was no request retry.

The first synthetic prompt requested a short model-chosen codeword; the second asked for the codeword from the immediately preceding answer without supplying it. The private plan fixed both prompts, `endolocal` / `nanbeige4.3-33b`, one child, a 120-second overall limit, a 60-second second-approval idle limit, a 1 MiB request-wire limit, a 2 MiB RPC-output limit and a 10 MiB aggregate transfer cap. PASS required two separately approved, complete exchanges in the same owned session, exact retained first-response context, no extra requests or tools, intact lineage and a verified final receipt. First-only completion would be partial; an unavailable prerequisite or approval would be gated; a definite contract violation would fail; a post-dispatch timeout or disconnect could leave the outcome unknown. Semantic answer agreement was a supporting check, not the definition of continuity.

The task-owned server used llama.cpp build 11518, commit reported as `1f8fa5231`, with executable SHA-256 `2c4c7139b339fbe1c10d02f5d8e5464e2cecf91658b2c335b29ddd648d18af68`. ## Evidence and outcome

The reader rechecked the parent and selected child, plan and two approvals, separate exclusive dispatch markers, runtime archives, provisional boundary and its final log prefixes, Pi identity, capture and trajectory. It found exactly two ordered authorized requests and two complete HTTP 200 responses; the approved first prompt and model matched, and the second request retained the captured first answer and its supported reasoning field in the required context and order, followed by the approved second prompt. It verified one Pi attachment and session across the turns, no forbidden tool or configuration changes or extra captured requests, and expected process-exit evidence. The independent reader returned `verified`, not merely the runner's in-process report. The runtime's live PID and process-group cleanup are local observations, not portable process attestation.

Both captured final answers were nonempty and matched after trimming surrounding whitespace. The generated codeword and reasoning are intentionally private. This semantic result is one observation, not evidence of determinism or general recall. Both responses contained supported reasoning fields; their exact retention in the second request was checked without publishing them.

The first and second responses reported 599 and 692 prompt tokens, and 65 and 37 completion tokens, respectively. The server reported 0 and 659 cached prompt tokens; those numbers do not establish KV-cache contents or causality. Approximately 24.4 seconds elapsed from the first approval timestamp to the end of the second captured response, including the operator's boundary review; this is not full startup-to-cleanup wall time. The proxy buffers complete responses and does not preserve normal upstream streaming timing, so these observations are not an interactive latency measurement.

## Scope and next steps

This result establishes one locally verified, governed two-turn continuation in a fresh Pi session with this profile and model. It does not prove operating-system isolation, historical process or KV-cache restoration, arbitrary branch execution, deterministic behavior, causal equivalence, or behavior with other providers and response formats. The private system-entry content is not independently compared with the corresponding captured system message. The no-tools profile is not an OS sandbox.

An optional external-effect isolation backend should be evaluated separately with its own threat model and tests. A useful next governed study is matched initial-sibling A/A execution, with fresh plans, approvals and predeclared measurements; a controlled single-variable A/B can follow only after its baseline and measurement design are reviewed. VERIFY and EVOLVE may eventually consume such observations through explicit evidence and promotion policies, but this single acceptance does not authorize autonomous promotion or establish causal effects.
