# Matched two-turn A/A: implementation feasibility only

Status: **GATED**. This is not a live A/A result and is not an approval to start one. No model request or real Pi session was made for this work. The comparison reader, study coordinator, private study commitment, and the required adversarial workflow tests are not yet implemented. Individual verified continuation receipts alone do not establish a valid matched study.

## Inherited evidence and feasibility

The prior [real acceptance](../REAL-ACCEPTANCE.md) reports one separately approved, tool-free Pi 1.0.4 / Nanbeige4.3-33B session, two real completion requests and a verified receipt independently checked in a fresh process. Its private evidence is not published. The earlier [initial-child pilot](../../governed-initial-child/1.0.4/RESULTS.md) was a four-request **single-turn** pilot, not a two-turn A/A study. It observed request-body differences attributable to a uniquely identified cwd and reported narrowly cwd-adjusted equality only as a diagnostic.

The continuation API independently re-verifies the qualified source, replay and both pristine prepared siblings, and derives a fresh runtime outside the sibling directories for each attempt. Its plans bind distinct attempt IDs, source and replay generations, parent and child, condition, Pi identity, model, prompts and budgets. Its independent receipt reader checks the two approvals, dispatches, captured exchanges, same-session continuation and retention of the first response. It does not compare different attempts or independently prove external model weights or server settings. The branch conditions are declarations: the only supported runtime manipulations are no change and `thinkingLevel: off`; equal declarations do not by themselves prove equal external environments. The earlier continuation fixture's alternative declares `thinkingLevel: high` and is not a matched arm.

The new offline feasibility test creates one fresh sibling pair with distinct condition IDs and identical `thinkingLevel: off` settings. For both ABBA and BAAB, it runs four separate fake-Pi two-turn sessions against a local fake OpenAI endpoint, creates separate synthetic approvals and receipts, independently verifies each receipt, and checks that both siblings remain pristine after each attempt. It checks four distinct attempt IDs, four distinct session IDs and eight fake requests per ordering. These are automated controls, not human approvals or real inference. The existing verifier establishes the within-session retention condition for each accepted fake receipt. The test does not implement or validate a study-level comparison reader, study-level order commitment, operator workflow, response scoring or external-environment parity.

## Required work before live execution

1. Commit a private, immutable study plan before dispatch: exact prompts and deterministic expected token, seed and selected ABBA or BAAB sequence, qualified parent and freshly prepared matched sibling identities, full budgets and explicit server observations. Bind each attempt to its position and plan without publishing private prompts or keys. Record an initial source/sibling verification and verify them again after the study.
2. Add a bounded sequential coordinator that uses the existing continuation runner and requires the operator to enter both exact phrases for every attempt. Verify each closed receipt and owned-resource cleanup before continuing; stop on uncertainty, failed parity or feasibility gate. Never retry a dispatched attempt. The first pair is a feasibility gate, not permission to skip later approvals.
3. Add an independent read-only comparison process which re-verifies each receipt against current source and siblings, rejects duplicate attempt/session IDs, incorrect order or role, changed generation, condition, prompts, model, executable and budgets, and checks effective request parameters and no-tool surface. Verify model file, server process and configuration separately; receipt validity alone cannot establish those facts. Capture omissions explicitly.
4. Extract bounded private measurements from verified captures: exact request hashes and lengths, responses and task scores, usage and cached-token reports, reasoning presence/length and clock boundaries. Compare second requests by common structure and within-session retention rather than demanding identical bytes. Normalize cwd only where the particular field and replacement are uniquely identified and independently grounded; preserve raw equality and classify all other differences. Produce a separately redacted report.
5. Exercise the complete workflow with fake Pi and endpoint, including stale or tampered source, siblings, receipts and transcript; duplicates, unequal conditions and models; prompt/tool changes and extra dispatch; missing approval; disconnected, partial, timeout and unknown outcomes; unsupported framing or reasoning; and a wrong answer in a valid receipt. Confirm cleanup affects only owned resources. The feasibility test here is not a substitute for these controls.
6. Revalidate Pi, model file, loopback endpoint, server settings and GPU resources. Starting a task-owned server requires the operator's explicit approval. Each turn needs its own exact operator-entered phrase. If an outcome is unknown after dispatch, stop and preserve evidence; do not rerun it. A verified first pair without a second pair is a feasibility result, not a completed study.

A future A/A PASS must mean the preregistered governed procedure completed and was independently verified, not that all answers match. With two sessions per arm, report descriptive observations only. Shared server state, order, GPU load, caching, omitted sampling parameters and fresh process/RNG/KV state limit interpretation. Identical answers do not establish determinism; differing answers do not establish an effect of sibling identity; reported cached tokens do not prove cache savings.

No A/B treatment is supported by this feasibility test. Once a valid A/A baseline exists, a candidate smallest next study is a separately preregistered change to one supported sampling parameter, provided both the runtime and the independent reader can verify its effective value; the current governed condition surface does not yet support that manipulation.
