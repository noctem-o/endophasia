# DEVELOP-ISOLATE-001: verified offline Bubblewrap diagnostic (partial)

**Status: partial, offline diagnostic only.** This does not enable Everyday, change Strict, or turn Protected’s refusal into a launch. A separate process passing preflight does not establish protection for the Pi process the workbench actually talks to.

## Architecture and threat model

The trusted controller, its terminal and the canonical evidence store stay outside the sandbox. The intended boundary is unprivileged Bubblewrap (empty read-only root, explicit mounts, new mount, user, PID, net, IPC and UTS namespaces, fresh terminal session, no capabilities or further user namespaces). A transient systemd user scope registers the wrapper before it starts and confirms cleanup, including detached processes. A scope neither restricts filesystem access nor makes an unsandboxed agent safe. The first slice uses the existing experiment runner for a bounded, disposable offline session, not the live workbench launcher.

Treat prompts, the paired page, Pi tool code, descendants, plugins, MCP settings, and workspace content (including Git metadata) as hostile. The test profile admits only explicitly selected root-owned runtime files and a private disposable workspace. It does not bind the operator’s home, evidence stores, checkout, host `/run`, package caches or `/sys`. Inside it may write the workspace and private tmpfs; Git fixture metadata is read-only. Settings are synthetic; a private Pi agent directory replaces the real one. Pipes are the only controller channel. The shared runner starts a new terminal session via its detached spawn; Bubblewrap’s `--new-session` is defense in depth, not required for the observed result. The runner closes inherited descriptors before `systemd-run`, preserving just stdio and the three Bubblewrap control channels. In the diagnostic and protected-experiment preflight a trusted read-only observer inventories the descriptors before Node startup. There is no model endpoint, bridge, listener or host network route. A separate net namespace matters for host abstract Unix sockets as well as loopback.

Enforcement assumes a trusted kernel, Bubblewrap, systemd user manager, controller, and root-owned runtime and dependencies (including the host’s Python sanitizer and the probe-only Bash observer). It assumes the local operator and other host processes with the operator’s authority do not race setup or tamper with the test. It excludes kernel vulnerabilities, resource exhaustion beyond the configured limits, side channels, host-admin inspection, malicious bytes later opened or executed by the operator, and compromise of the controller or its parsers. Bind-source paths can appear in mount metadata. Kernel keyrings and extra syscall filtering are not isolated by this profile; allow no real credentials until these are addressed. It does not protect processes started outside this boundary. It must not be used on a checkout whose Git admin directory, sockets, nested mounts or hardlinked inodes can alias host resources.

## Gates before workbench integration

1. **Mount selection and Git.** A canonical workspace path is not an inode boundary. A bind of arbitrary working trees can include nested mounts, hardlinks, pathname sockets and Git administration links. Start with a fresh disposable workspace, or establish a race-safe admission and pinning policy. Read-only `.git` here is a fixture control, not a guarantee for linked worktrees, nested repositories or arbitrary checkout content. The workbench’s `GitProjectInspectorV0` runs Git and reads untracked files as the operator. Its existing Git flags and config overrides are useful hardening, not an OS boundary for hostile mutable content; run inspection inside confinement (including file reads), or omit it in a future contained workbench. Do not hand this diagnostic’s workspace to the host inspector.
2. **Actual process and subject.** Reuse `ProcessScopeV0.wrap` for a live keeper, but separately join the ready handshake to the exact Pi process (PID and birth identity, not a PID alone), its verified namespaces/mounts, workspace identity, private descriptors and RPC transport. Prevent in-boundary code from minting its own attestation. The attached session ID and canonical workspace root must match at each grant decision. Missing, stale, contradictory or replaced identity must fail closed; tests of the existing broker policy are not evidence that a production observer is attached. No live provider or authority changes are part of the diagnostic.
3. **Runtime and extension policy.** Arch’s `/usr/bin/pi` resolves to a Node bundle under `/usr/lib/node_modules/@earendil-works/pi-coding-agent`. The bundle also uses packaged assets/dependencies; a single CLI file is not a complete Pi runtime. Admit only a trusted installed release; validate the whole runtime/config closure and do not load workspace or operator extensions, skills, prompts, themes or MCP configuration in the first pilot. A writable fixture home must never become a host runtime/config source.
4. **Model access.** The existing experiment relay is designed for one declared OpenAI-compatible local route, over a private Unix socket with host-side admission. It needs an approved listener and upstream, and does not provide a credential-safe generic route to external providers. The network stays isolated and no credential material is staged. The only supported real Pi probe in this change is credential-free RPC startup and state; it is not an Everyday pilot.
5. **Descriptors in the actual live launch.** Reuse the shared runner’s fd hygiene or an equally strict pre-exec allowlist; observe the exact fd inventory for the executing Pi path. A file, device, pipe or connected socket descriptor can bypass path and namespace boundaries. Do not infer the descriptor table of a live launch from a different process’s preflight.

No privileged socket was contacted or tested and no live Pi configuration was inspected.

### Automated checks and simulations

Five new tests cover malformed, stale and substituted probe output, exact negative-control outcomes, lost/incomplete execution, and a simulated kernel refusal before containment starts. The existing broker suite exercises invalid, mismatched and lost session protection and unchanged Strict approvals with stand-ins. These tests do not establish isolation for Pi. The 119-test focused run included the new tests, the existing session-control suite, Git inspector, and process containment. One existing test was excluded because its final assertion probes permissions on real privileged socket paths. Typecheck, lint (one unchanged warning in `tests/endo-cockpit-eighteenth-review.test.ts`), and build passed. The full suite, live workbench, and legacy network preflight were not run because they open listeners; no full-suite comparison with `main` is claimed.

### Operator procedure: offline Pi RPC smoke

Run from this draft’s checkout on the same unprivileged Arch workstation. Confirm the installed Pi is the pinned root-owned 1.5.2 package at the documented path; do not use the normal Pi home, a real checkout as workspace, or any provider credentials. The controller needs its ordinary user manager and cgroup v2, not elevated authority. Both commands create and clean disposable fixtures and transient user scopes, with no services or listeners:

```sh
script -q -e -c 'node research/develop-isolate-001/diagnostic.ts' /dev/null
script -q -e -c 'node research/develop-isolate-001/diagnostic.ts --operator-approved-offline-pi' /dev/null
```

Run the second command only if the first exits 0 and reports `controllerTTY: true`, and only on explicit approval to start real Pi. The second runs the trusted baseline and controls first, then starts Pi in a **separate** sandbox with the pinned package read-only at `/pi`; no model, no tools, ephemeral session, private home, and only one fixed `get_state` call over pipes. It plants synthetic extension and MCP config canaries in the private home; insist on `pi-rpc: state`, `pi-process: same-namespace-and-workspace`, both marker checks `ENOENT`, non-truncated output and confirmed termination. Marker absence is evidence only for this startup path; there is no positive extension/MCP activation control yet. Pi shares the smoke’s PID namespace and uid with the observer, so that smoke report could be forged; the earlier trusted baseline has already exited and cannot be rewritten by Pi. Neither report is live attestation for a workbench session. Stop at any refusal or discrepancy; do not broaden mounts, share the network or weaken flags.

**There is no safe Everyday or model-backed pilot command in this draft.** Before one is run, a new change must cover the integration gates above, include an adversarial test of live Pi substitution/loss at the broker, and specify the authorized model destination, scoped credentials, request ceilings and shutdown. Until then, keep the production provider at `not-enforced` and the existing mode fallback and refusal unchanged.
