# Linux host profile inspection: real admission gated

This research-only host profile probe never establishes server parity and never grants execution authority. The [task-owned provenance mechanism](TASK-OWNED-PROVENANCE.md) reuses this probe for a server the launcher itself started and feeds the A/A admission hook and an offline reader; it does not change what the probe can establish, and the standalone command is still not wired to the plan. No real inference was performed. Real admission remains gated.

On little-endian Linux the probe accepts an explicit PID, literal IPv4 loopback endpoint, executable and GGUF paths, expected SHA-256 digests, model alias and GPU-layer value. It reads the selected process's actual `/proc/PID/cmdline` and initial `/proc/PID/environ`, validates a strict argument and environment-name allowlist, and does not persist unrelated environment values or raw argv. It checks start ticks, boot and network namespace identities, the IPv4 listening socket and a matching selected-process descriptor, the running executable's filesystem identity, and mapped GGUF ranges, offsets, permissions and file identities. It hashes the opened executable and model under a time limit and rechecks the process, arguments, environment snapshot, files, mapping and listener. The historical binary digest is pinned, but does not prove build provenance. Linux exposes the process's initial environment through procfs; a match does not establish all later runtime settings.

The structured result distinguishes `MATCH`, `MISMATCH`, `UNAVAILABLE` and `UNSUPPORTED` by field. It separately reports a selected PID's matching FD, sampled IPv4 and IPv6 listeners in the same network namespace, a bounded scan of visible process descriptors, sole ownership, and the socket's reuse-port option. Any IPv6 listener on the port or multiple IPv4 listeners is refused. A second visible process holding the socket is refused; unreadable or disappearing descriptors make the visible-owner scan unavailable. Sole ownership remains `UNAVAILABLE` even if that scan succeeds, because procfs can hide processes in other PID namespaces. Consequently the command never reports `OBSERVABLE_MATCH`.

`/proc/net/tcp` and `tcp6` list sampled sockets; they do not themselves establish process ownership or socket options. Linux [sock_diag](https://man7.org/linux/man-pages/man7/sock_diag.7.html) can enumerate socket identities but does not solve shared-process ownership. On x86-64 and arm64, a bounded, fixed Python helper tries [pidfd_getfd](https://man7.org/linux/man-pages/man2/pidfd_getfd.2.html), checks the duplicated descriptor's socket inode and reads `SO_REUSEPORT` with `getsockopt`. The kernel applies a ptrace access check. Missing Python/kernel support, denied permission, timeout or malformed output produce `REUSEPORT_UNVERIFIED`; the probe never requests elevation or changes the server. A positive option value is refused. The helper's interpreter and locally observed facts remain within the trusted-host boundary.

All observations are samples: a listener, process, descriptor or file can change after inspection, and metadata checks cannot detect every in-place change. Timers cannot interrupt a synchronous filesystem syscall already blocked in the kernel. The command performs no HTTP requests or inference, and does not start, stop, or alter a server. It prints a redacted status and writes details exclusively to an owner-only private directory pinned by file descriptor.

The enforced profile is named `llama.cpp-11518-explicit-fit-off-v0`: it requires explicit `--fit off` and the other enumerated flags. The historical acceptance report instead records a fit target of 1024 MiB and does not establish an equivalent fit-off invocation. The profiles must not be treated as equivalent. The probe validates a sampled invocation, not undocumented defaults or effective runtime configuration. It does not query server-reported metadata or GPU telemetry, create real versioned admission evidence, or independently verify it from a fresh study reader. Fake local process tests exercise host observations only; a fake process is not a llama.cpp server or a real attestation provider. Neither the profile nor historical hash establishes source-to-binary provenance, GPU-resident bytes, RNG or KV state.

The candidate flag names were checked against the [server documentation at the previously reported llama.cpp commit](https://github.com/ggml-org/llama.cpp/blob/1f8fa52318b594b373e7447a3c2bb36cdba9515f/tools/server/README.md). That documentation describes available options; it does not establish the effective state of any running process.

The explicit command form is:

```text
node research/governed-initial-continuation/aa/inspect-linux.ts --pid PID --endpoint http://127.0.0.1:PORT --executable /absolute/server --executable-sha256 HEX --model /absolute/model.gguf --model-sha256 HEX --model-alias ALIAS --gpu-layers N --output /private/new-evidence.json --timeout-ms MILLISECONDS
```

The output parent must be owner-only. The command never starts Pi or a server, does not load a model, and contacts no endpoint. No next live step is authorized by this partial result.
